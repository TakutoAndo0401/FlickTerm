# コミットと push を行う

## 概要

変更内容を確認し、Conventional Commits に従って適切にコミットを作成する。すべてのコミットが完了し、検証に問題がない場合は push まで実行する。

## PR 作成時のルール

ユーザーが push 後に PR 作成まで依頼した場合は、PR タイトルには AI モデル名・AI サービス名・AI ツール名を示す prefix を付けない。

- 禁止例: `[codex]`, `[cursor]`, `[claude]`, `[copilot]`, `Codex:`, `Cursor agent:`, `Claude:`, `Copilot:`, `AI:`, `Generated by ...`
- GitHub plugin / GitHub connector / `gh pr create` / 他 skill の既定値に AI ツール名 prefix が含まれる場合でも、このルールを優先して削除する
- PR タイトルは変更内容そのものを簡潔に表す

## コミット前の準備

### 1. 変更内容の確認

```bash
git diff
git status
```

### 2. 変更内容の分析

- **修正・追加・削除**など複数の差分ファイルがあり、対応している内容が全く異なる場合は、**それぞれコミットを分けること**
- 各変更箇所と変更内容の詳細を把握する

## コミットメッセージのルール

### Conventional Commits 形式

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### Type の種類

- **feat**: 新機能
- **fix**: バグ修正
- **docs**: ドキュメント変更
- **style**: コード品質・フォーマット（機能変更なし）
- **refactor**: リファクタリング
- **test**: テスト追加・修正
- **chore**: ビルド・依存関係・設定変更
- **perf**: パフォーマンス改善
- その他: 任意のタイプが使用可能（team/projectで自由に定義）

### Scope の例

- `package`: パッケージ更新
- `config`: 設定ファイル変更
- Scope は **オプション**（省略可能）

### Description の規則

- **日本語で記述**
- **簡潔でわかりやすく、可能な限り短いメッセージ**
- 末尾にピリオドを付けない
- 命令形で記述（〜した ではなく 〜する）
- 説明は **必須**

### Breaking Changes（破壊的変更）

破壊的変更を含む場合は、以下の方法で記述：

**方法1: type/scope の後に `!` を追加**

```
feat(payment)!: API の支払い処理を完全に再設計

この変更により、既存の支払い処理フローは動作しなくなります。
新しい API エンドポイントを使用してください。
```

**方法2: footer に `BREAKING CHANGE:` を記述**

```
feat(payment): API の支払い処理を完全に再設計

BREAKING CHANGE: 既存の支払い処理フローは動作しなくなります。新しい API エンドポイントを使用してください。
```

### Body と Footer（オプション）

- **Body**: 変更の詳細な背景、理由、技術的詳細を記述
- **Footer**: 関連 Issue、レビュアー情報などを記述（Git trailer 形式）

例：

```
feat(campaign): キャンペーン検索機能を追加

キャンペーンの名前・日時・ステータスで検索できるようになりました。
検索結果はリアルタイムで更新されます。
```

## コミット実行例

### 例1: 新機能の追加

```bash
git commit -m "feat(section-help): よく検索されるキーワードにフィルター機能を追加"
```

### 例2: バグ修正

```bash
git commit -m "fix(inquiry-form): フォーム検証エラーメッセージが表示されない問題を修正"
```

### 例3: ドキュメント更新

```bash
git commit -m "docs: コミットガイドを更新"
```

### 例4: パッケージ更新

```bash
git commit -m "chore(deps): パッケージを最新バージョンに更新"
```

### 例5: テスト追加

```bash
git commit -m "test(keyword-button): KeywordButton コンポーネントのテストケースを追加"
```

### 例6: 破壊的変更（Breaking Change）

```bash
git commit -m "feat(auth)!: 認証 API を OAuth 2.0 に移行

従来の JWT ベースの認証は削除されます。
詳しくは MIGRATION.md をご覧ください。"
```

### 例7: 詳細な Body を含む例

```bash
git commit -m "refactor(campaign): キャンペーン検索処理を最適化

検索結果のキャッシング機能を追加しました。
これにより検索パフォーマンスが 50% 向上します。"
```

### 例8: Scope なし（全体的な変更）

```bash
git commit -m "docs: プロジェクト README を更新"
```

## コミット実行時の注意事項

### ✅ 必ず実行する

- [ ] コミットメッセージは日本語で記述し、できるだけ簡潔に記述する
- [ ] **type を必ず付ける**（feat, fix, docs, test, refactor, chore, perf, style など）
- [ ] **description を必ず記述する**
- [ ] Conventional Commits 仕様に従う
- [ ] commitlint でエラーが出た場合は適切に修正
- [ ] **変更が残っている限り繰り返しコミットする**（未コミットの変更がなくなるまで続ける）
- [ ] すべてのコミットが完了し、検証に問題がない場合は `git push` まで実行する

### ⚠️ 推奨（オプション）

- [ ] 複雑な変更の場合は Body を記述（変更理由・技術的詳細）
- [ ] 破壊的変更がある場合は明示的に記述（`!` または `BREAKING CHANGE:` footer）

### ❌ 絶対に行わない

- `--no-verify` オプション付きでのコミット

## CommitLint エラーが出た場合

```bash
# 直近のコミットメッセージを修正
git commit --amend -m "fix(keyword-button): 正しいメッセージ"

# 修正後、検証に問題がなければ push する
```
